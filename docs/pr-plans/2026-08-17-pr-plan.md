### Phase 2 driver — provider-aware prompt caching (from `docs/cachedinput`)

Goal: **reduce Cathedral's actual LLM COGS** when a user performs multiple generations against the same project/context.

**Business rule (hard constraint):** cache savings belong to Cathedral. Do NOT reduce the customer's generation charge because a provider cache hit occurred. Customer billing continues using Cathedral's normal published input/output rates.

Internally, separately track the true provider cost using:
- normal input tokens
- cached-read input tokens
- cache-write input tokens
- output tokens
- tool costs

This lets caching increase Cathedral's margin without changing user-facing pricing.

   Rule: any character in `character_deltas[].character_name` with no explicit `injuries`/`status='deceased'`/`status='dying'` is treated as ALIVE. System-prompt rule: "absence of death signal = presumed alive; do not require an explicit `alive=true` field".

   ```
   /(is |are )?(dead|dies|died|kill(ed|s)?|deceased|gone|missing|absent)/i
   /(wiped? out|massacred|executed|assassinated|murdered)/i
   ```
   Extract character names from the surrounding ±60 chars. Build `explicitClaims: [{ character_name, claim_kind, source_text }]`. Inject into the user prompt as a labelled block above the LLM call:
   ```
   EXPLICIT DEATH/MISSING CLAIMS DETECTED IN PROPOSED SECTION:
     - "Ted": source="Ted and Fred and Betty are dead now" (claim kind: dead)
   ```
   The LLM then compares against ALIVE/DEAD/INJURED lists in accepted sections.

3. **Drop "be sparing" guardrail on explicit claims.** System prompt change:
   > If the proposed section explicitly claims a character is dead, killed, missing, or absent, AND that character appears in ALIVE list in any accepted section, emit a `character_state` warning with `severity: 'high'` citing the contradicting section. This is a HIGH-confidence flag and should NEVER be silently dropped.
   For weak/implicit signals (theme echoes, stylistic proximity, speculative concerns), still be sparing.

4. **CANON MEMORY block in user prompt.** Explicitly surface the structured memory inputs so the LLM sees what fields are available:

   ```
   Characters (ALIVE by default — only DEAD/INJURED if explicitly flagged):
     - Ted: alive (no death signal)
     - Fred: alive (no death signal)

     - ...
   Character positions at end of Smoke Test:
     - Ted @ somewhere (immediate_state)
   ```

   Verifies "correct data inputs" requirement before the LLM reasons.

## Phase 2 — Provider-Aware Prompt Caching (cost optimization)

### Why this matters (from `docs/cachedinput`)

The reference spec at `docs/cachedinput` (commit `6d4c471`, 238 lines) sets out the cost-saving vision: cache the **stable** portion of every generation's prompt against the project identity so a project's Nth generation reuses ~80% of the prior generation's input tokens. Customer charge stays normal; only Cathedral's margin improves.

### Design intent (from `docs/cachedinput`)

Refactor prompt assembly conceptually into 4 parts:

1. **Craft instructions** — Cathedral writing behavior, container instructions (general + per-container).
2. **Stable project context** — premise, characters, relationships, setting/world rules, themes, motifs, story spark, prompt-pack/project-level instructions, other long-lived project context.
3. **Current story state** — cumulative character state, plot threads, continuity facts, open loops, latest ending state.
4. **Current generation request** — generate/regenerate/continue/remix, previous output, terminal beat, current section, current writing task, other volatile data.

**Stable prefix is deterministic.** No timestamps, request UUIDs, random ordering, or transient values appear before the cache boundary.

Initial cache boundary: **Craft + Stable Project Context → break → Story State + Current Request**. Single break is enough until a provider API makes multiple-breaks materially simpler.

Provider-side implementation:
- **OpenAI**: stable project-scoped `prompt_cache_key`, explicit caching/breakpoint (`cache_control` markers).
- **Anthropic, Gemini**: stub providers, real adapters later.

**Token accounting:** `uncached = total input − cached reads − cache writes`, clamped at zero. Add cache-write usage/pricing where required.

**Billing:** keep two calculations separate:
- **Customer charge** uses Cathedral's normal generation pricing. NEVER discount for a cache hit.
- **Actual provider COGS** uses provider's real reported usage:
  `uncached × normal rate + cached reads × cached rate + cache writes × cache-write rate + output × output rate + tool costs`.

**Preflight:** keep assuming zero cache savings (cache hit is not guaranteed, only count it after the provider responds).

**Goal:** refactor prompt into stable/volatile, add project cache identity, enable first cache boundary. **No user-visible pricing changes.**

Inject cache-control markers (`{ type: "ephemeral" }` boundary) at the right slice.
- `supabase/functions/generate-story/_provider.ts` — extend `OpenAI` provider to:

  - Inject OpenAI's `prompt_cache_key` field on the request.
  - Map Cathedral's cache breakpoint concept to OpenAI's per-message `cache_control`.

**Code-level changes:**

1. **`buildPrompt` returns structured blocks.** Add a `cacheSupported: boolean` parameter to `buildPrompt`. If true, return `{ stableBlocks: PromptBlock[], volatileBlocks: PromptBlock[] }`. If false (unsupported model), concatenate as before (no cache boundary).

2. **`OpenAI` provider translates to OpenAI's schema:**
   ```ts
   messages: [
     ...stableBlocks.map(b => ({ role: "user", content: b, cache_control: { type: "ephemeral" } })),
     ...volatileBlocks
   ],
   prompt_cache_key: cacheKey  // stable project-scoped key
   ```

3. **`cacheKey` derivation in `index.ts` (caller side):**
   ```
   cacheKey = `cath:proj:${projectId}:v1`
   ```
   The `:v1` suffix is the schema version. Bumping (`:v2`) gives OpenAI a fresh cache namespace when prompt structure changes (no fragmentary invalidation).

4. **Stable prefix determinism checks** (test stubs):
   - Same `projectId`, `outlineId`, no other changes → byte-identical prompt prefix.
   - Changing `terminalBeat`, `previousOutputText`, `beatLabel`, model → prompt volatile suffix changes, stable prefix unchanged.
   - No `Date.now()`, `crypto.randomUUID()`, or per-request IDs in the stable path.
   - `default<T>` order in JSON serialization must match a fixed schema (the schema is the stable contract).
